# Data Dictionary — Campus Lost & Found

## Provenance
All files here are **synthetic sample data**, generated by
`generate_dataset.py` with a fixed random seed (42) for reproducibility.
No real student reports, personal data or photos are included, in line
with the module's "no personal or proprietary data" requirement. The
generator produces 105 lost item reports and 105 found item reports
across 8 item categories (Bottle, Keys, Card, Bag, Umbrella, Earphones,
Jacket, Watch), with a known ground-truth mapping used to evaluate the
TF-IDF matching engine in analytics/match.py.

To regenerate: `python3 generate_dataset.py` (run from the data/ folder,
or `python3 data/generate_dataset.py` from the project root).

## data/lost_items.csv (105 rows)

| Field | Type | Description |
|---|---|---|
| id | string | Unique identifier for the lost item report (primary key) |
| category | string | Item category, one of the 8 types listed above |
| description | string | Free-text description given by the reporter |
| location | string | Free-text location where the item was last seen |
| date_lost | date (YYYY-MM-DD) | Date the item was reported lost |
| reporter_role | string | student / staff |

## data/found_items.csv (105 rows)

| Field | Type | Description |
|---|---|---|
| id | string | Unique identifier for the found item report (primary key) |
| category | string | Item category, same value set as lost_items.category |
| description | string | Free-text description given by the finder |
| location | string | Free-text location where the item was found |
| date_found | date (YYYY-MM-DD) | Date the item was handed in |
| held_by | string | Which Security post is currently holding the item |

## data/ground_truth.csv (105 rows)

| Field | Type | Description |
|---|---|---|
| lost_id | string | Foreign key to lost_items.id |
| found_id | string | Foreign key to found_items.id, or empty if this lost item has no true counterpart in the dataset |

85 of the 105 lost items have a true matching found item; 20 do not
(included deliberately so the evaluation can measure both precision on
real matches and the false-positive rate on items that should get no
suggestion).

## Fields used by the TF-IDF matcher
`category`, `description`, and `location` from lost_items.csv and
found_items.csv are concatenated into one text field per report before
vectorisation. `id`, dates, `held_by` and `reporter_role` are metadata
only — not fed into the model. ground_truth.csv is used only for
evaluation, never for training/fitting the vectoriser.

## Known limitations of this dataset
- Only 8 item categories with a small, fixed set of phrasings per
  category. This means two *different* items of the same category (e.g.
  two different black umbrellas) can produce text nearly as similar as a
  *true* lost/found pair. This directly caused the matching engine's
  precision to be much lower than an initial 4-row pilot suggested (see
  evidence/test-data-ai.md for the full analysis) — a known, honestly
  reported limitation of both the dataset and the TF-IDF method.
- Descriptions are template-based rather than freely written, so they
  understate the messiness of real user input (typos, abbreviations) but
  also understate the amount of genuinely distinguishing detail a real
  reporter might include (a scratch, a sticker, a serial number).
